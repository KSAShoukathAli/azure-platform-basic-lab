Chapter 1 - Foundations

Friday, Oct 30 2026, evening session. Steps 1 to 7.

Late in the session we moved two working resources into a module. Nothing about them changed. Same names, same settings, same resource group. Just a code reorganization.

Terraform's plan said: Plan: 2 to add, 0 to change, 2 to destroy.

It wanted to delete the storage account and create a new, empty one. For a refactor. If we had typed yes, a real team would have lost data on a Friday night and spent the weekend explaining it.

Two small moved blocks later, the same plan read 0 to add, 0 to change, 0 to destroy. Everything in this chapter leads up to understanding why both of those plans were correct.

The mental model that made everything click

Every plan does the same three things, in this order. Once this landed, drift, import, state rm and the "already exists" error all stopped being separate topics.

The corollaryTerraform does check Azure on every plan, but only for resources already in its state. Anything outside state is invisible. That is the root of the import lesson and the module-move lesson.

Step 1 - State storage with az CLI

DidCreated rg-tfstate-ksa, storage account sttfstateksa01 (TLS 1.2, no public blob access), turned on blob versioning and 7-day soft delete, created the tfstate container with az storage container-rm create, and gave myself Storage Blob Data Contributor on the account.

SawRunning az storage account create a second time said "found, will continue to update the existing account." Nothing broke.

WhyTerraform needs somewhere to write state before it can create anything. If Terraform had to create its own state storage, it would need the storage to start and would need to start to create the storage. That's the chicken-and-egg. We solved it by creating the storage outside Terraform. The book solves it differently: create the bucket with local state first, then add the backend and let terraform init copy the local state into it.

Book's wayOur way
Who creates state storageTerraform (two steps, state migration)az CLI (one step)
Is it in Terraform state?YesNo - Terraform only points at it
RiskA careless destroy can delete the storage holding the stateTerraform can't delete what it doesn't know about
Why the data roleOwner or Contributor lets you manage the storage account (management plane). Reading the blob with Entra login (use_azuread_auth = true) is the data plane, which needs Storage Blob Data Contributor. In a pipeline, the same role goes to the pipeline's app registration, scoped to the tfstate container, plus Contributor where it deploys.

Step 2 - The smallest config, with remote state

DidOne resource group in main.tf, a terraform {} block with the provider version and backend, and provider "azurerm" { features {} }. Subscription from $env:ARM_SUBSCRIPTION_ID. Then init, plan, apply. Later split the backend into its own backend.tf.

SawInstalled hashicorp/azurerm v5.12.0. Acquiring state lock / Releasing state lock on every plan and apply. No terraform.tfstate in the folder; the blob azure-platform-basic-lab/infra.tfstate in the container instead.

Why~> 5.0 picked the newest 5.x, and .terraform.lock.hcl pins exactly 5.12.0 so every machine and pipeline uses the same build. The lock messages are the blob lease: while one person runs, nobody else can write that state.

Piece.NET equivalentJob

Step 3 - Change, drift, replace, import

3b changeAdded an owner tag. Plan showed ~ update in-place. Used terraform plan -out tfplan then terraform apply tfplan: no prompt, because you're applying exactly what you reviewed. Pipelines always do this.

3c driftAdded a costcenter tag with az CLI. terraform plan wanted to remove it. Code wins. terraform plan -refresh-only showed it under "Objects have changed outside of Terraform" and proposed no Azure change.

3d replaceChanged the region to eastus. Plan showed -/+ with # forces replacement. Not applied. A resource group can't move regions.

3e importCreated stbasiclabksa01 with az CLI. Plan said No changes - Terraform couldn't see it. Wrote the resource block plus an import block with the Azure ID. Plan: 1 to import, 0 to add, 1 to change. The one change was + public_network_access = "Enabled": az CLI never set that newer property, and the provider fills in its default. Behavior unchanged. Applied, then deleted import.tf.

SymbolMeaningRisk
+createlow
~update in placelow to medium - read what changes
-/+destroy then recreatehigh - look for # forces replacement
-destroyhigh
plan vs plan -refresh-onlyBoth refresh from Azure. Plan compares against code and apply fixes Azure. Refresh-only compares against the old state and apply fixes state only. Refresh-only never accepts drift - only changing the code does. Use plan -refresh-only often to look; apply -refresh-only rarely, when you need state updated but changing Azure right now would be wrong (investigating a deletion, or another stack reading your outputs).
ignore_changesWhen something else legitimately owns a value - autoscale instance count, tags added by Azure Policy - put it in lifecycle { ignore_changes = [...] }. Terraform stops comparing that attribute, and normal applies keep state accurate. No refresh-only needed. Catch: it also ignores your own code changes to that value.
Import vs "just add the code"Without import, code has the resource and state doesn't, so plan shows + create. On apply, azurerm checks first and fails with "A resource with the ID ... already exists - to be managed via Terraform this resource needs to be imported into the State." Reproduced it with terraform state rm (removes from state only, Azure untouched), then fixed it with the CLI form terraform import. The import block is preferred: it shows in plan and goes through review.

Step 4 - Variables

DidMoved name, region and tags into variables.tf with types, defaults and a validation rule. Values in terraform.tfvars.

SawNo changes after the refactor. A bad storage name failed with my own error message. TF_VAR_resource_group_name lost to tfvars; TF_VAR_location beat the default and planned replacement of both resources. Removing tfvars with -input=false gave "No value for required variable".

WhyThe storage account was replaced too, even though only the region variable changed, because its location came from azurerm_resource_group.main.location. References carry changes through the dependency graph.

-Nothing: Terraform prompts. Pipelines use -input=false so they fail instead of hanging.

Step 5 - Locals

DidReplaced the two name variables with app_name, environment, name_suffix. Built names and common_tags in locals.tf using interpolation and merge(). Moved the storage name rule into a lifecycle { precondition }, since locals can't have validation. Added outputs.

Sawterraform console showed the built names matched exactly, so the plan had only ~ tag updates. Apply ran in dependency order: resource group, then storage account. -var="app_name=orders" renamed everything at once and forced replacement.

The ruleIf a person should choose it, variable. If it can be calculated, local. Variable = method parameter. Local = local variable inside the method, never settable from outside.

Step 6 - Into a module, without destroying anything

DidCreated modules/app-foundation (versions, variables, locals, main, outputs - no provider, no backend). The root became one module "foundation" call, with outputs passed through. Ran init to register the module.

SawWithout moved: 2 to add, 2 to destroy - "because azurerm_resource_group.main is not in configuration". With moved.tf: "has moved to module.foundation...", 0 to add, 0 to change, 0 to destroy. After apply, state list showed the new addresses. The storage account still had its original creation time, 00:40 UTC, from the az CLI step.

WhyMoving code into a module changes the address: azurerm_storage_account.data becomes module.foundation.azurerm_storage_account.data. State holds the old address, code holds the new one, and Terraform can't know they're the same thing. moved renames the entry in state. Azure is never touched. Note the refresh lines already showed the new addresses: moved blocks are applied to state in memory before refresh.

Step 7 - Dev and test

FoundA bug in the module: names didn't include the environment, so dev and test would both produce rg-basiclab-ksa. Typical - a module works with one caller and breaks with two.

Didterraform plan -destroy then terraform destroy on the lab env (storage first, then RG - reverse dependency order). Deleted infra/ and its state blob (recoverable 7 days thanks to soft delete). Fixed naming to rg-basiclab-{env}-ksa / stbasiclab{env}ksa01, added a replication_type input. Created envs/dev (LRS) and envs/test (ZRS), each with its own backend key.

SawTest's first plan said 2 to add even though dev already existed - its own state was empty. Added a tag in dev: dev planned 2 to change, test said No changes. Two blobs: dev.tfstate and test.tfstate.

The backend key is the wall between environmentsSame container, different blob. Copy dev's backend into a new environment and forget to change the key, and the new environment reads dev's state.

Questions that came up

What changes when this runs from GitHub Actions?
No az login user. The workflow logs in as an app registration via OIDC (federated credential tied to repo + branch, no secret). That identity needs Storage Blob Data Contributor on the state container and Contributor where it deploys (plus RBAC Administrator if Terraform creates role assignments).
Are the client, tenant and subscription IDs secrets?
No. They're identifiers, like a username with no password. They go in GitHub vars. The proof of identity is the short-lived OIDC token. The workflow maps them to ARM_CLIENT_ID, ARM_TENANT_ID, ARM_SUBSCRIPTION_ID, ARM_USE_OIDC=true for Terraform.
Why both required_providers and a provider block?
One downloads the plugin, the other configures it. One plugin can have many provider configurations (aliases), for example app subscription and shared DNS subscription.
Does terraform init read the subscription?
No. Init connects the backend and downloads providers. The provider reads the subscription during plan and apply.
How does this look with separate subscriptions per environment?
Dev and QA often share a non-prod subscription; staging and prod get their own. Per environment: different subscription, different pipeline identity (only allowed into its own subscription), and prod state in its own restricted storage. With folder-per-env, pin subscription_id in each env's providers.tf so a leftover shell variable can never send a dev apply into prod. The backend has its own subscription_id, so state can live in a management subscription.

Mistakes and fixes

Plan files committed to a public repo.gitignore had *.tfplan, but the files were named tfplan with no extension, so nothing matched. infra/tfplan went in during steps 4-5, and envs/dev/tfplan, envs/test/tfplan in step 7. A saved plan contains a prior-state snapshot, which can include storage keys. Fix: added tfplan to .gitignore, git rm --cached, and rotated dev and test storage keys. The lab account whose keys could be in history was already destroyed. Rule: if a secret might be exposed, rotate first, then decide about history.
CRLF warningsWindows Git converting line endings. Added .gitattributes with * text=auto eol=lf, since Actions runners are Linux.
